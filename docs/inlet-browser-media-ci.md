# Codec-Qualified Browser Validation

PR130 hosted run37412515307/job112103881519 selected `Chromium154.0.8037.0` before Google Chrome. The real campaign review tests failed on both databases waiting for the uploaded MP4's first decoded frame. FFmpeg6.1.1 server decode cases passed. The previous driver reported only the timed-out condition, so it did not establish the exact browser MediaError.

The runner's [official installer](https://github.com/actions/runner-images/blob/main/images/ubuntu/scripts/build/install-google-chrome.sh) installs an unbranded Chromium snapshot alongside branded Chrome. Chromium's [codec documentation](https://www.chromium.org/audio-video/) distinguishes proprietary H.264/AAC support from default Chromium build support. Local Debian Chromium includes these codecs, so its passing playback was not sufficient qualification for the runner snapshot. The exact snapshot revision1689415 download was blocked by this environment's network proxyHTTP403, including a request with additional network permission. Do not claim that exact binary's MediaError was reproduced locally.

The repair makes installed-name detection insufficient for CI. `scripts/check_browser_media.py` generates actual synthetic H.264 MP4 clips, with and without AAC, then loads each as a private-style blob in each distinct installed browser. It prints only synthetic media diagnostics: browser/version, canPlayType, load/error event, MediaError code/message, readyState and frame width. Selection requires both loadeddata events, readyState>=2, width64 and no MediaError. It writes the passing executable to `INLET_TEST_BROWSER` through GitHub's environment file; all browser tests consume it. No installed browser that actually decodes both means CI failure, never a skip. Branded Chrome is preferred when multiple builds qualify.

The original real authenticated campaign journey still uploads, creates the draft, retrieves bounded private bytes, verifies actual decoded width and blob URL, rejects unavailable media, and verifies object-URL revocation. No playback assertion or timeout was relaxed. Its timeout now includes bounded media-state diagnostics. No production UI, server validator, content policy or provider behavior changed.
