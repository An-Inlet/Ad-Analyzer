# Configured Existing-Campaign Optimization

This package assembles Google and Meta existing-campaign budget/pause APIs with the
actual owned native catalog, separately admitted server evidence, private credential
contexts and durable optimization coordinator. It does not install a live evidence
source. TikTok discovery remains unavailable pending its documented native schema
qualification. Existing creation/activation and legacy v1 hashes remain unchanged.

Server settings are `optimization_execution_manifest_path`,
`optimization_execution_manifest_digest` and `optimization_operating_policy_path`.
The loader pins the manifest and exact required operating-policy digest. The trusted
Python registry remains empty. Missing configuration/source returns unavailable.
No JSON proof, callback import, inferred qualification or default numeric policy is
accepted. Real network transport rejects contract scenarios before constructing a
transport or evidence factory; offline tests explicitly inject only that HTTP seam
and a typed, labeled scenario source. These are not live qualification results.

Each request binds the original principal/session and the actual application engine.
The generator owns an ExitStack; the credential context alone owns its transport.
Provider dispatch gates the typed scope before any factory or credential work.
Private sessions release locks before OAuth/native HTTP and recheck original session
and source generation afterwards. The API rechecks goal/scope and observation expiry
before storing anything. Policy pins are per-process cached immutable configuration;
this package does not claim file hot reload or global cross-process revocation.

## Customer Flow And Authority

The frozen API is described in `design/configured-optimization-customer-api.md`.
Customers choose named admitted options and confirm total, named aggression and
scope. All freshness/cooldown/action/derived-cap numbers come from the explicit server
policy. Preparation writes the immutable marked financial revision and exact0080
sidecar in one transaction, then checks original authority again before committing.
The SQLite service preflight requires enabled foreign keys;0080 also physically
checks the exact deferred FK and discriminator in its database guard.

Consent refreshes actual native inventory and separate admission. Exact source
identity/revision/evidence commitment, goal, scope, native state, policy and intent
must remain the same. A native inventory envelope includes observation timestamps;
the retained original inventory digest remains an audit commitment, while fresh
inventory is independently recollected/validated. It is not compared byte-for-byte
solely to force equal observation time. Qualification provenance uses its explicit
`evidence_digest`, with ID/revision and all scope/money checks retained. Real state
or qualification-revision changes require a fresh preparation.

After consent, review discovery explicitly uses the original real mandate binding
and period, not a fabricated financial horizon. Exact review/approval and current
account/goal/payment/exposure/ledger gates remain. Every forward optimization path
uses the current origin guard. Generic marked consent without a trusted guard and
configured legacy technical-knob routes deny. Legacy explicit test runtimes retain
compatibility; no legacy consent is silently promoted. The new guard performs only
local checks under locked forward boundaries, never provider HTTP.

Original period/currency/account-set accounting, high-water consumption and held
reservations remain unchanged. An edit cannot raise the existing overall cap.
Ambiguous emission retains the original attempt/fence/hold; recovery only reads that
original request and never treats old state or absence as permission to replay.
Historical receipts/reconciliation and existing settlement semantics remain retained.
The optional replacement port is delegated only when the manifest admits it and the
trusted source supplies it. No new settlement endpoint or empirical closure evidence
is invented here; production repeat/settlement qualification remains separate.

## Verification Scope

The genuine API fixture starts with customer identity, confirmed goal and owned
connections, but no provider mandate/review/attempt/hold. It uses real vault opening,
MockHTTP inventory, admission, reads and native mutation/readback through ordinary
configured dependencies. Time advances15 seconds before consent and10 before review.
Google/Meta budget, pause and unknown-request journeys run on SQLite/PostgreSQL.
Separate tests cover revocation/generation/source change during HTTP, generic/technical
bypass rejection, exact provenance export, cap rejection, atomic rollback after both
inserts and real-transport scenario denial. No runtime-getter overrides are used.

This is offline implementation evidence, not a live spending mandate, proven native
financial cap, deployment or completed launch qualification. The customer UI/TLS
composition is a separate dependent package using the same frozen APIs.
