# Google Reporting Runtime — 2026-10-12

Baseline `076695d5b0b225a2ff706ccff4caf4e585236201`; local branch
`codex/inlet-w1-followup`. This package closes the real application's always-None
Google reporting dependency, composing existing customer range, event-selection
and capture services through existing credential interfaces. It does not activate
reporting, change credentials or select a production planning policy.

## Scope And Defaults

`INLET_CUSTOMER_GOOGLE_REPORTING_ENABLED` defaults false and the example leaves it
false. Existing `google_read` mode, exact v24 and complete client/developer/Vault
configuration are independently required. Factory construction performs no IO.
The lazy transport permits only HTTPS POST to the fixed Google token-refresh and
v24 customer read-search endpoints; it rejects advertising mutation paths, foreign
origins, alternate ports and non-refresh OAuth forms. Forms have byte/field bounds,
with blank or duplicate fields rejected. Owned inner transports close at client exit
and reopen for subsequent calls/pages rather than reusing a closed HTTPTransport.

Availability callbacks fence provider IO, replays and each final range/selection/
capture commit. Current original-session, tenant/account, grant, generation, privacy,
aggregate, selection, mapping and deadline checks remain. Late disablement rolls
back staged rows; state and explicit invalidation remain available while disabled.
No advertising write-capable provider is composed.

TikTok count support was considered first. The accessible official SDK establishes
the synchronous endpoint but does not establish the exact website-purchase metric /
report-type / data-level / dimension combination. Known official metric/dimension
gateway reads were inaccessible here; earlier research explicitly retains that gap.
TikTok was not promoted to supported, and no value units or effective attribution
were invented. See [contract](design/google-reporting-runtime-v1.md) and external
`/workspace/inlet-evidence/20261012/tiktok-count-research/`.
